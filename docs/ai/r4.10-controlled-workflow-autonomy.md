## 1. Executive Summary & Objective

SYNCORA AI Release 4.10 bridges intelligence with bounded, policy-governed execution. Prior releases established semantic retrieval, durable jobs (Release 4.5), organizational memory & decision outcomes (Release 4.6), security hardening (Release 4.7), production observability (Release 4.8), and personalized evidence grounding (Release 4.9). 

Release 4.10 evolves SYNCORA AI into a system that can reliably execute bounded multi-step workflows under typed, deterministic autonomy policies. The core premise is **controlled autonomy, never unrestricted autonomy**:
- The model proposes structured workflow plans.
- Trusted server logic evaluates risk, enforces permissions, and checks workspace autonomy policy.
- Automatic execution is limited strictly to pre-approved, allowlisted low-risk mutations within explicit bounds.
- High-risk, destructive, or ambiguous operations strictly require explicit human approval.
- Execution is protected by cryptographic plan digest binding, authoritative pre/postcondition verification, LIFO compensating transaction journals, and server-side kill switches.

### Component Directory & Responsibilities
- **`src/lib/ai/autonomy.ts`**: Formal typed autonomy model (`AutonomyLevel`: 0, 1, 2, 3), deterministic policy evaluator (`evaluateAutonomyDecision`), plan canonical digest computation (SHA-256), and server-side kill switch verification.
- **`src/lib/ai/workflow-approval.ts`**: Plan digest binding (`WorkflowApprovalRecord`), cryptographic tamper detection, approval expiration, workspace tenant boundary checks, and revocation.
- **`src/lib/ai/workflow-verification.ts`**: Authoritative execution-time precondition checks (stale state and project/user existence checks) and postcondition verification against authoritative PostgreSQL tables.
- **`src/lib/ai/compensation.ts`**: LIFO compensating transaction journal recording and automated rollback execution to safely revert partial multi-step failures without human intervention.
- **`src/lib/ai/workflow-executor.ts`**: Durable execution engine orchestrating concurrency leases, idempotency skipping, event publication, and high-level `executeGovernedWorkflow`.
- **`src/lib/ai/governance.ts`**: Workspace AI policy management with `autonomy_level` (default 1), `allowed_autonomous_actions`, and `max_autonomous_actions_per_workflow`.
- **`src/app/api/ai/action/execute/route.ts`**: Server-side human approval binding upon manual confirmation, connecting approval records with plan digests.

## 3. The Autonomy Model

SYNCORA AI defines four explicit autonomy levels:

| Level | Name | Allowed Capabilities | Mutation Allowed? | Approval Required? |
| :--- | :--- | :--- | :--- | :--- |
| **0** | **Advisory** | Read context, analyze overdue tasks, produce proposed plan preview | **NO** | N/A (Cannot mutate) |
| **1** | **Prepare & Request Approval** | Generate structured plan, calculate plan risk, bind plan digest, request human review | Only after approved | **YES** (Mandatory before execution) |
| **2** | **Bounded Automatic Execution** | Automatically execute pre-approved allowlisted low-risk actions within configured bounds | **YES** (Bounded) | **NO** (If within policy bounds) |
| **3** | **Restricted High-Impact Execution** | Unrestricted tool execution, arbitrary scripts, mass deletion | **STRICTLY PROHIBITED** | N/A (Fails closed) |

### Non-Negotiable Invariants:
1. **Conservative Defaults:** Default autonomy level for all existing and new workspaces is **Level 1** (`PREPARE_AND_REQUEST_APPROVAL`).
2. **Deterministic Governance:** An LLM cannot self-escalate autonomy, self-approve plans, or declare actions safe.
3. **High-Risk Hard Precedence:** Regardless of workspace autonomy setting (even Level 2), high-risk or destructive actions (such as `delete_task`) **strictly require human approval**.
4. **Execution Bounds:** Any plan exceeding `max_autonomous_actions_per_workflow` (default 3) automatically drops back to Level 1 requiring human confirmation.

## 4. Approval Integrity & Cryptographic Plan Binding

Human approval must never be a generic token or blank check. In Release 4.10:
- When a plan is proposed, SYNCORA computes a canonical SHA-256 hash digest of all steps, tools, arguments, and dependencies (`computePlanDigest`).
- The human approval record in `ai_action_logs` binds `workflowId`, `workspaceId`, `approverId`, `planDigest`, and `expiresAt`.
- At execution time, `validateApprovalIntegrity` recomputes the plan digest against the approved record:
  - **Plan Alteration (Tamper Defense):** If arguments, order, or dependencies were altered after approval was given, execution is immediately aborted with `PLAN_ALTERED_AFTER_APPROVAL`.
  - **Expiry:** Approvals expire after a configurable TTL (default 60 minutes). Expired approvals fail closed.
  - **Tenant Boundary:** An approval granted in Workspace Alpha can never be executed or replayed in Workspace Beta.

## 5. Verification & Compensation Semantics

### 5.1 Preconditions
Before executing any mutation:
- The target task or project must exist and belong to the authenticated workspace.
- The resource state is compared against `expectedState`. If an external user changed the task status in the meantime, the step aborts prior to mutation to prevent overwriting newer human changes.

### 5.2 Authoritative Postconditions
Step completion is not assumed from tool return payloads. Instead:
- Authoritative PostgreSQL state is queried immediately following execution.
- If the database state fails to reflect the expected transition, the step is marked `needs_review` and transitions the workflow to `VERIFICATION_FAILED`.

### 5.3 Compensating Transactions (LIFO Journal)
When a multi-step workflow experiences a failure on a subsequent step (e.g. Step 2 fails after Step 1 succeeded):
- The executor consults the in-flight `CompensationEntry[]` journal.
- Safe, verified compensating updates are executed in reverse order (LIFO) to restore pre-mutation state.
- Compensation is verified against current authoritative state to avoid clobbering concurrent user edits.

## 6. Server-Side Master Kill Switch

Operators can instantly shut off all autonomous execution across an entire workspace or globally:
- **Environment Variable:** `AI_AUTONOMY_KILL_SWITCH=true` immediately halts all Level 2 autonomous execution across all tenants.
- **Workspace Policy Flag:** Setting `kill_switch_active: true` in `ai_workspace_policies` immediately down-negotiates all requests in that workspace to Level 1 (requiring explicit human confirmation).
- Fails closed server-side; UI state cannot bypass or override the kill switch.

## 8. Deployment Runbook & Operational Safety

1. **Deployment Sequence:**
   - Deploy codebase with default policy (`autonomy_level: 1`).
   - Run verification checks against staging database.
   - For workspaces wishing to test Level 2 autonomy, tenant administrators must explicitly update their workspace policy via `PUT /api/ai/governance` to set `autonomy_level: 2` and define `allowed_autonomous_actions`.
2. **Rollback Procedure:**
   - In case of operational anomaly, activate `AI_AUTONOMY_KILL_SWITCH=true` in environment variables.
   - All pending workflows will immediately revert to human approval without needing code redeployment.
