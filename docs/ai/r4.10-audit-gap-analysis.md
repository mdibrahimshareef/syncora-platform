## 2. Existing Architecture & Workflow Infrastructure Map

### 2.1 Workflow Planning & Execution Engine
- **`src/lib/ai/workflow-schema.ts`**: Defines Zod schemas:
  - `WorkflowStateSchema`: `PLANNING`, `AWAITING_APPROVAL`, `EXECUTING`, `VERIFYING`, `PAUSED`, `RECOVERING`, `COMPLETED`, `PARTIALLY_COMPLETED`, `CANCELLED`, `CANCELLATION_REQUESTED`, `FAILED`, `VERIFICATION_FAILED`.
  - `RiskLevelSchema`: `LOW`, `MEDIUM`, `HIGH`.
  - `WorkflowStepSchema`: `stepId`, `tool`, `args`, `dependsOn`, `expectedState`, `risk`.
  - `WorkflowPlanSchema`: Enforces max 5 steps, acyclic dependency validation, unique step IDs.
- **`src/lib/ai/workflow-state.ts`**: Validates legal state transitions via `isValidWorkflowTransition` and `isValidStepTransition`.
- **`src/lib/ai/workflow-executor.ts`**:
  - Leases: 2-minute sliding lease with 15-minute hard timeout (`timeout_at`).
  - Idempotency: `ai_action_logs` checked per `planId-stepId` composite key before executing.
  - Concurrency: CAS updates on `ai_workflows` matching executor ID.
  - Lifecycle: `executeWorkflowPlan`, `resumeWorkflowPlan`, `cancelWorkflowPlan`, `retryWorkflowStep`.
- **`src/lib/ai/action-executor.ts`**: Executes individual tools (`create_task`, `update_task`, `assign_task`) with workspace validation, stale state checking, and postcondition verification.
- **`src/lib/ai/risk.ts`**: Classifies tool risk (read = `LOW`, mutations = `MEDIUM`, destructive/permission = `HIGH`) and plan-level risk.

### 2.2 Background Job Queue & Dispatcher
- **`src/lib/ai/dispatcher.ts`**: PostgreSQL-backed job queue with `claim_ai_job` RPC (`FOR UPDATE SKIP LOCKED`). Manages retry exponential backoff (`next_attempt_at`), max attempt caps (default 3), and lease recovery for abandoned jobs.
- **`src/types/ai-jobs.ts`**: Typed `AIJob` and `AIInsight` entities with statuses `QUEUED`, `CLAIMED`, `RUNNING`, `WAITING_APPROVAL`, `RECOVERY_PENDING`, `COMPLETED`, `FAILED`, `CANCELLED`, `EXPIRED`.

### 2.3 Governance & Policy Engine
- **`src/lib/ai/governance.ts`**:
  - `getWorkspaceAIPolicy`: Reads `ai_workspace_policies` table with conservative fallback.
  - `validateAIRequest`: Checks `ai_enabled`, daily request quotas from `ai_usage_metrics`, and active concurrent workflow limits (`max_concurrent_workflows`).
  - Enforces tool toggles: `allow_ai_task_creation`, `allow_ai_task_assignment`, `allow_ai_task_updates`.

## 3. Specific Safety Gaps Identified in Existing System

1. **Absence of a Formal Autonomy Model:**
   The current code operates under an all-or-nothing model: actions either run in the background (proactive jobs) or require interactive user button confirmation in the chat UI. There is no typed concept of Autonomy Levels (Level 0: Advisory, Level 1: Approval-Gated, Level 2: Bounded Automatic Execution, Level 3: Prohibited High-Impact).

2. **Policy Lacks Autonomy Bounds & Emergency Kill Switch:**
   `WorkspaceAIPolicy` lacks fields for:
   - `autonomy_level` (0, 1, 2, 3),
   - `allowed_autonomous_actions` (strict allowlist of tool names permitted for Level 2 execution),
   - `kill_switch_active` (server-side master switch to immediately disable all autonomous mutations across a workspace or globally),
   - `max_autonomous_actions_per_workflow` (action ceiling when running autonomously).

3. **Approval Plan Tampering Vulnerability:**
   When `executeAction` or `executeWorkflowPlan` is called via `/api/ai/action/execute`, the endpoint receives `args` (the plan) from the client request body. There is no cryptographic digest or immutable hash (`planDigest`) verifying that the executed plan is identical to what was generated and approved.

4. **Lack of Automated Precondition & Postcondition Engine:**
   While `action-executor.ts` has ad-hoc checks for `tasks`, there is no standardized precondition verification phase before workflow execution begins. Stale resources, deleted projects, or changed assignee permissions could result in partial mutations before detecting an error.

5. **No Compensation or Rollback for Reversible Steps:**
   When step 2 of a 3-step workflow fails, the workflow enters `PARTIALLY_COMPLETED`. However, previous reversible mutations (such as a status update or label change) are not safely recorded in a compensation journal, preventing automated or human-approved rollback.

6. **Ambiguous Outcome Recovery:**
   If a network connection drops after an action mutation succeeds in the database but before the action log records `completed`, a subsequent retry could re-attempt a non-idempotent action unless strict pre-execution verification is conducted.

## 4. Minimal Proposed Implementation for Release 4.10

### Module 1: Typed Autonomy Model & Policy Extensions (`src/lib/ai/autonomy.ts`)
- Define `AutonomyLevel`: `0 | 1 | 2 | 3`.
  - **Level 0 (Advisory):** Read-only analysis; all mutations prohibited.
  - **Level 1 (Approval-Required):** Plans generated and validated; human must sign off via bound approval.
  - **Level 2 (Bounded Automatic Execution):** Pre-approved, low-risk, reversible actions executed automatically if policy, bounds, and preconditions pass.
  - **Level 3 (Restricted High-Impact):** Prohibited in R4.10.
- Extend `WorkspaceAIPolicy` with:
  - `autonomy_level: AutonomyLevel` (default: `1`),
  - `allowed_autonomous_actions: string[]` (default: `['update_task']`),
  - `kill_switch_active: boolean` (default: `false`),
  - `max_autonomous_actions_per_workflow: number` (default: `3`).
- Implement `evaluateAutonomyDecision` returning `{ allowed, effectiveLevel, requiresApproval, reasonCodes, bounds }`.

### Module 2: Plan Digest & Approval Integrity (`src/lib/ai/workflow-approval.ts`)
- Implement `computePlanDigest(plan: WorkflowPlan): string` using deterministic SHA-256 over canonicalized plan step definitions.
- Require and verify `planDigest` on approval creation and execution. If any step, parameter, or dependency changes, the digest mismatches and execution is blocked.

### Module 3: Precondition & Postcondition Verification Engine (`src/lib/ai/workflow-verification.ts`)
- Standardized verification lifecycle:
  - `verifyPreconditions(supabase, workspaceId, step): Promise<VerificationResult>`
  - `verifyPostconditions(supabase, workspaceId, step, executionResult): Promise<VerificationResult>`
  - States: `succeeded`, `failed`, `unknown`, `needs_review`.

### Module 4: Compensation & Journaling (`src/lib/ai/compensation.ts`)
- Step-level compensation journal: captures snapshot of resource before mutation.
- `compensateWorkflowStep`: Executes inverse mutation if step is reversible and safe.

### Module 5: Hardened Workflow Executor Integration (`src/lib/ai/workflow-executor.ts`)
- Check workspace autonomy policy and kill switch prior to running.
- In Level 2, automatically execute allowlisted low-risk steps without requiring human approval.
- Enforce strict limits and rollback on partial failure.

### Module 6: Evaluation Suite V3 (`tests/ai/evals/r4.10-controlled-autonomy.test.ts`)
- 15 deterministic multi-turn scenarios covering all autonomy dimensions.

## 5. Explicitly Excluded Features

To maintain stability and security, the following are strictly excluded from Release 4.10:
- Unrestricted Level 3 autonomy (no autonomous deletions, permission changes, or destructive operations).
- Autonomous agent swarms or dynamic tool synthesis.
- Third-party external API mutations outside existing Supabase-backed tables.
- Parallel un-synchronized step execution.
