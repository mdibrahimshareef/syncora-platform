# SYNCORA AI - RELEASE 4.2 AUDIT

## 1. Current Architecture Findings
- **Idempotency**: `ai_action_logs` currently acts as an idempotency table for individual action execution.
- **Workflow State**: The workflow execution logic (`workflow-executor.ts`) is currently ephemeral in-memory. If the server crashes, the workflow state is lost (though individual step idempotency is preserved in the database).
- **Workflow Engine**: Iterates through steps sequentially, validating dependencies, calculating risk, and checking authorization.
- **Verification**: `action-executor.ts` returns `executed_but_not_verified` if verification fails post-mutation.
- **UI Monitor**: `WorkflowPlanCard.tsx` renders static execution logic without real-time step visualization.

## 2. Existing Realtime Capabilities
- **Supabase Realtime**: The platform relies heavily on Supabase Realtime for collaboration (`realtime_collaboration.sql`). It streams changes directly from Postgres tables to the client.

## 3. Existing Persistence Capabilities
- **ai_action_logs**: Used for idempotency. Primary key is `action_id`.
- **ai_conversations**: Used for storing chat history.
- **No durable event stream**: There is no table that stores a timeline of what happened (e.g., `STEP_STARTED`, `STEP_COMPLETED`).

## 4. Exact Gaps for R4.2
- **Durable Event Stream**: The lack of an append-only event stream prevents real-time observability of step-by-step progress. We cannot easily resume a workflow if the server drops the request without knowing exactly what state the overarching workflow was left in.
- **Authoritative Workflow State**: Workflows do not have an overarching state persisted in the DB (only individual steps have state in `ai_action_logs`).
- **Retry Mechanism**: No granular logic for retrying a failed step from the UI.
- **Cancellation**: No mechanism for cancelling a workflow midway through execution.
- **Real-Time UI**: `WorkflowPlanCard.tsx` doesn't subscribe to execution events.

## 5. Proposed Minimal Schema Changes
`ai_action_logs` is structurally a key-value idempotency store (`action_id` is PK). We cannot safely convert it to an append-only event stream without violating the idempotency constraints or creating a confusing polymorphic schema.
Therefore, a new table `ai_workflow_events` is genuinely required.

**`ai_workflow_events` Schema:**
- `id` (UUID, PK)
- `workflow_id` (TEXT, NOT NULL)
- `step_id` (TEXT, NULL)
- `workspace_id` (UUID, NOT NULL)
- `user_id` (UUID, NOT NULL)
- `event_type` (TEXT, NOT NULL)
- `status` (TEXT, NOT NULL)
- `sequence` (BIGINT, NOT NULL) -- For ordering and reconciliation
- `metadata` (JSONB)
- `created_at` (TIMESTAMPTZ)

**`ai_workflows` Schema (Optional but recommended for state tracking):**
Alternatively, we can track the overall workflow state in `ai_workflows` and rely on Supabase Realtime on `ai_workflow_events`. For maximum durability, `ai_workflows` would hold the final canonical state. Let's create both: `ai_workflows` (current state) and `ai_workflow_events` (event stream).

## 6. Proposed State Machine
**Workflow States:**
`PLANNING` → `AWAITING_APPROVAL` → `EXECUTING`
`EXECUTING` → `VERIFYING` | `PAUSED` | `COMPLETED` | `PARTIALLY_COMPLETED` | `FAILED` | `CANCELLATION_REQUESTED`
`PAUSED` → `RECOVERING` | `CANCELLED`
`RECOVERING` → `EXECUTING` | `PARTIALLY_COMPLETED`
`CANCELLATION_REQUESTED` → `CANCELLED`

**Step States:**
`PENDING` → `EXECUTING`
`EXECUTING` → `VERIFYING` | `FAILED` | `CANCELLED`
`VERIFYING` → `COMPLETED` | `FAILED`
`FAILED` → `RETRYING` | `SKIPPED`
`RETRYING` → `EXECUTING`
