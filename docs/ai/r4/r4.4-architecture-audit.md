# R4.4 Architecture Audit

## 1. Existing Workflow State Machine
- Controlled by `isValidWorkflowTransition` in `workflow-state.ts`.
- Transitions: `PLANNING` -> `AWAITING_APPROVAL` -> `EXECUTING` <-> `PAUSED` / `RECOVERING`.
- Terminal states: `COMPLETED`, `CANCELLED`.
- Atomic concurrency lock implemented in `workflow-executor.ts` via `.update().in('status', [...])`.

## 2. Existing AI Execution Pipeline
- Chat requests orchestrated by `src/lib/ai/orchestrator.ts`.
- Workflow plans generated via `generate_workflow_plan` tool.
- Steps executed via `executeAction` in `action-executor.ts` using idempotency tokens (`ai_action_logs`).
- Real-time updates pushed via `ai_workflow_events`.

## 3. Existing Telemetry
- `logAITelemetry` in `telemetry.ts` logs structured JSON to stdout.

## 4. Current Gaps for R4.4
- **Governance**: No centralized layer to reject requests based on policies or limits.
- **Rate Limiting**: Missing. Needs database-backed counters or token buckets.
- **Cost/Usage**: Telemetry logs usage but no DB tracking for quota enforcement.
- **Policies**: Workspace AI policies don't exist.
- **Timeouts/Limits**: `orchestrator.ts` has a simple Vercel timeout, but workflows need hard max-step / execution limits.
- **Organization Control**: No existing tables for AI config per workspace/org.

## 5. Proposed Approach
- Create `ai_workspace_policies` table to store workspace configurations (enabled, max steps, etc.).
- Create `ai_usage_metrics` table to track usage windows for rate limiting and cost accounting.
- Implement `src/lib/ai/governance.ts` as a middleware/guard invoked at the start of orchestrator, workflow creation, and workflow execution.
- Add `workflow.expires_at` or `lease_expires_at` to `ai_workflows` to handle stale active executor claims.
