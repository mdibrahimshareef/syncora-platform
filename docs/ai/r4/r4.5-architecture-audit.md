# R4.5 Architecture Audit & Implementation Plan

## 0. Context & Objectives
Release 4.5 transitions Syncora AI from a **reactive, user-triggered workflow system** to a **durable, proactive, governed agent runtime**.

R4.1–R4.4 established the orchestration kernel, recovery logic, workflow control plane, and strict governance (rate limits, workspace AI policies, budgets). R4.5 wraps this foundation in a durable Job Queue and Dispatcher to allow background execution, crash recovery, and proactive insight generation without bypassing any existing safety constraints.

## 1. Durable AI Job Model
Currently, workflows are initiated directly via HTTP API endpoints, executing in serverless function memory. If the execution crashes or the Vercel function times out, the lease expires and the workflow stalls until the user manually resumes it.

**New Schema (`ai_jobs`):**
To provide a durable runtime, we introduce an `ai_jobs` table in Postgres:
- `id` UUID PRIMARY KEY
- `workspace_id` UUID (FK to workspaces)
- `user_id` UUID (FK to users, for policy validation)
- `job_type` TEXT (`EVENT_TRIGGERED`, `SCHEDULED`, `PROACTIVE`)
- `trigger_type` TEXT (`task.overdue`, `project.status_changed`, `cron`)
- `payload` JSONB (input arguments)
- `status` TEXT (`QUEUED`, `CLAIMED`, `RUNNING`, `RECOVERY_PENDING`, `COMPLETED`, `FAILED`, `CANCELLED`, `EXPIRED`)
- `priority` INTEGER (higher runs first)
- `executor_id` TEXT (node/worker ID claiming the job)
- `attempt_count` INTEGER DEFAULT 0
- `max_attempts` INTEGER DEFAULT 3
- `scheduled_at`, `claimed_at`, `started_at`, `completed_at`, `failed_at`
- `lease_expires_at`, `next_attempt_at`
- `created_at`, `updated_at`

## 2. Dispatcher & Crash Recovery
The **Agent Dispatcher** will be a scheduled/polling mechanism (e.g., via Next.js Cron or external scheduler pinging a secure endpoint) that:
1. Atomically claims `QUEUED` jobs where `scheduled_at` <= NOW() (or is NULL).
2. Uses Postgres atomic updates (`UPDATE ai_jobs SET status = 'CLAIMED', executor_id = $1... RETURNING *`) to prevent duplicate claims.
3. Once claimed, it validates governance (`validateAIRequest`) and initiates execution.
4. Updates status to `RUNNING` and sets `lease_expires_at`.
5. Upon completion or failure, updates the job status appropriately.

**Crash Recovery:**
A separate background process (or the dispatcher itself) will query for jobs stuck in `CLAIMED` or `RUNNING` where `lease_expires_at < NOW()`. These are transitioned to `RECOVERY_PENDING`. Next time the dispatcher picks them up, they are retried if `attempt_count < max_attempts`, re-validating all idempotency checks.

## 3. Event-Triggered AI & Scheduling
**Event-Triggered:** R14 deterministic automations (`automations` and `automation_runs`) exist and work flawlessly. Rather than rebuilding them, we simply add a new automation action (`ai.invoke_job`). When a deterministic automation fires (e.g., Task goes overdue), it inserts an `ai_jobs` record.
**Scheduled:** We will support basic cron execution by creating `SCHEDULED` jobs with a `scheduled_at` timestamp.

## 4. Proactive Work Intelligence
Instead of waiting for a user to prompt "What should I do?", the system proactively detects risks. 
We will introduce an `ai_insights` table:
- `id` UUID PRIMARY KEY
- `workspace_id` UUID
- `type` TEXT (`NEEDS_ATTENTION`, `PROJECT_AT_RISK`, `SUGGESTED_NEXT`)
- `entity_type` & `entity_id` (context references)
- `content` TEXT (The insight itself)
- `action_proposed` JSONB (Optional executable action)
- `confidence` INTEGER
- `is_dismissed` BOOLEAN

**Integration:** These insights will be fed into the existing `notifications` table (with type `AI_INSIGHT`), notifying users natively through Syncora's existing UI. 

## 5. Security & Governance Boundaries
**Strict Rule:** The dispatcher is a *triggering mechanism*, not an execution bypass.
- When the dispatcher executes a job, it MUST impersonate the `user_id` and pass through `/api/ai/governance`.
- Read-only insights can be generated autonomously.
- Mutating actions (e.g., `create_task`) proposed by proactive intelligence MUST route through the R4.1 `WAITING_APPROVAL` human-in-the-loop state.
- Idempotency (`ai_action_logs`) guarantees that if a job crashes midway, duplicate execution will silently skip completed steps upon retry.

## 6. Implementation Plan
1. **Schema Migration:** Create `ai_jobs` and `ai_insights` tables with appropriate RLS policies.
2. **Dispatcher Engine:** Implement the atomic queue, lease tracking, and recovery scanner.
3. **Automations Bridge:** Integrate with R14 automations to support `ai.invoke_job`.
4. **Insight Generator:** Build the scheduled `PROACTIVE` worker that analyzes workspace data and writes to `ai_insights`.
5. **Notification Hook:** Wire `ai_insights` into the `notifications` trigger.
6. **Admin Dashboard Extension:** Surface the job queue and metrics in the UI.
